# Final Engineering Summary

Per-run summaries are generated by the system itself (`SUMMARY.md` in each `scenarios/*/run-*/` folder, also
`GET /api/runs/{id}/summary`). This document is the submission-level summary.

## 1. Plan and rationale
Assignment emphasis is the orchestration layer, so effort went there; the URL shortener is deliberately small and serves
as the system under change.
1. Orchestration core: DAG with gates, stateful execution, governance, resilience, observability.
2. Agents behind a single `LlmGateway` seam (Spring AI in the app; deterministic mock offline).
3. Baseline application to make brownfield real; validation stage that builds and tests generated changes.
4. Three required scenarios plus re-plan and chaos runs as evidence.

## 4. Risks, failure scenarios and controls
| Risk / failure | Control | Evidence |
|---|---|---|
| Agent leaks a credential | `secret-scan` DENY, regenerate with feedback, never committed | chaos scenario; `leakedSecretIsDeniedAndNeverCommitted` |
| Agent writes outside workspace | `path-safety` policy + `WorkspaceWriter` refuses escape | `PolicyTest` |
| Destructive / schema change auto-applied | `high-impact-change` forces human approval, staged not committed | brownfield scenario; `humanApprovalIsRequiredForDestructiveMigration` |
| Transient agent / LLM failure | Bounded retries with backoff, timeout, fallback | chaos scenario; `transientFailuresAreRetriedWithinBound` |
| Permanent failure leaves inconsistent state | Wave atomicity + checkpoint rollback; run FAILED, resumable by human | `permanentFailureRollsBackWholeWave` |
| Runaway cost / loops | Attempt budget, rejection limit, resume limit, kill switch | `budgetExhaustionHaltsAndHumanCanResume`, `repeatedRejectionFailsTheRun` |
| Upstream change makes downstream stale | Consumer invalidation, early cutoff | `replanRerunsOnlyWhatChangedAndStopsAtUnchangedOutput` |
| Broken generated code reaches release | `build-validation` gate fails the run before release | `failingBuildStopsTheRunBeforeRelease` |
| Model-supplied shell commands | Engine-owned argv allowlist, no shell, scrubbed env, timeout | `runnerRefusesCommandsOutsideTheAllowlist` |
| Ambiguous requirement built on guesses | Clarification gate blocks design until answered (max rounds, then recorded assumptions) | ambiguous scenario |
| Prompt injection via repository/requirement text | Output is never executed directly; policies and gates act on output; human approval at design and release | partial, see limitations |

## 5. Assumptions
- Single-region, single-node prototype; H2 is acceptable for audit storage.
- Generated code targets Java 17 / Spring Boot 3, matching the baseline.
- Humans approve via the REST API; identities are asserted strings.
- Offline runs use the deterministic mock; model quality is out of scope for these runs.

## 6. Limitations (honest)
- **Build validation in the offline scenarios is SIMULATED** (labelled in every report). Real mode (`AGENTIC_VALIDATION=real`) runs allowlisted `mvn` commands but is process-level isolation only; untrusted code needs a container without network/secrets.
- Mock-generated code is canned and not meaningful to compile; real value appears with a real model + real validation.
- A failed build escalates to a human; there is no automatic repair loop.
- H2 persists the audit log; the **run aggregate is in memory** and is not rebuilt after restart.
- `advance()` is synchronous per HTTP request.
- Policies are pattern-based; the `BLOCKER:` security gate is a convention, not a SAST scan.
- Approvals have no authN/Z or four-eyes rule.
- Spring layer and `shortener-service` were not built in the authoring sandbox (no Maven access); see `docs/validation.md`.
